# site-check

내 사이트를 **로컬에서** 한 단계씩 검사하고, 찾은 것을 **대화로 보고만** 한다. 고치지 않는다.

## 지킬 것

- 대상은 사용자가 만든 프로젝트의 **로컬 실행본**(localhost)만. 운영 주소·남의 사이트에는 아무것도 보내지 않는다.
- 코드·테스트·설정을 고치지 않는다. 테스트 파일도 만들지 않는다(후보만 말한다).
- `.env`·키·비밀번호 값은 답이나 기록에 옮겨 적지 않는다. "어느 파일 몇 번째 줄"까지만.
- 설치가 필요한 도구가 없으면 설치 명령을 보여 주고 물은 뒤에만 설치한다. 거절하면 "건너뜀".
- 질문은 일반 메시지로 한다.
- 해커톤 키트에서 쓸 때: 마감 전 한 번만, 20분 안쪽으로 1·2(1번)·3·4(3·4번) 단계 위주로 돌린다. 브라우저를 직접 조작하지 않는다(대회 Computer Use 금지). 네트워크가 막히면 Semgrep·의존성 점검은 건너뜀.
- **단계는 하나씩 순서대로 돌린다.** 빌드·E2E·서버처럼 폴더나 포트를 건드리는 명령끼리 동시에 돌리지 않는다. 예외는 하나뿐: 2단계 1번 서브에이전트 검토는 읽기만 하므로 1단계를 시작할 때 백그라운드로 띄워 둬도 된다.
- 모든 명령은 **대상 프로젝트 폴더에서** 돌린다(`cd <대상> && …`). 세션 작업 폴더 기준으로만 도는 도구(예: 내장 `/security-review`)는 쓰지 않는다.
- 도구가 실패하면 그 단계에 적힌 대체 방법을 쓰고, 적힌 게 없거나 그래도 안 되면 이유를 적고 다음 단계로 간다. 실패한 도구를 "통과"로 세지 않는다.

## 0단계. 프로젝트 파악

1. README·package.json·requirements·docker-compose·playwright 설정을 읽고 정리한다:
   - 로컬 실행 방법(서버 몇 개, 포트, DB 필요 여부, 필요한 환경 변수, 개발용 로그인 여부)
   - 이미 있는 검사 명령: 단위 테스트, 타입 검사, 린트, E2E
   - 주요 사용자 흐름 3~5개(가입·로그인·핵심 기능·결제 등)와 **사람마다 따로인 것**(내 게임, 내 방, 내 결제 등 — 4단계 두 계정 시나리오에 쓴다)
   - 화면 밖 입구: API 경로 목록, 웹소켓, 웹훅, 업로드
2. 검사할 코드 상태를 적는다: `git rev-parse --short HEAD`, 브랜치, `git status --short`(작업 중 변경이 있으면 어느 파일인지).
3. 지난 기록 `docs/verify/site-check.md`가 있으면 읽어 둔다(5단계에서 비교).
4. 4단계에서 쓸 **임시 데이터 방법**을 정한다: 데이터 폴더·DB 주소를 환경 변수로 바꿀 수 있으면 새 임시 폴더나 새 DB 이름을 쓴다. 바꿀 방법이 없으면 4단계의 쓰기 동작(가입·만들기·두 계정)을 해도 되는지 사용자에게 묻는다.
5. 위 정리를 사용자에게 보여 주고 "이대로 검사할까요?" 한 번 묻는다. 키가 필요하거나 실행 방법이 불확실하면 여기서 묻는다.

## 1단계. 빠른 기본 검사 (몇 분, 결과가 매번 같음)

프로젝트에 있는 명령만 그대로 돌린다. 없으면 "없음"으로 적고 지어내지 않는다.

- 단위 테스트 (예: `npm test`, `pytest`)
- 타입 검사 (예: `npx tsc --noEmit`, 스크립트에 `typecheck`가 있으면 그것)
- 린트 (예: `npm run lint`)

통과 기준: 셋 다 종료 코드 0. 건너뛴 테스트(skip) 수도 적는다.

## 2단계. 코드 보안 검토 (사이트 안 띄움)

1. **서브에이전트 보안 검토** (필수). 일반 서브에이전트에게 대상 폴더 경로를 주고 읽기만 하게 맡긴다. 범위:
   - 기본 브랜치 대비 바뀐 것(`git diff origin/<기본 브랜치>...HEAD`; origin이 없으면 로컬 `main`/`master`, 둘 다 없으면 이 항목은 빼고 작업 중 변경만)과 작업 중 변경
   - 바뀐 것과 상관없이 늘 볼 곳: 로그인·권한 검사, 0단계의 화면 밖 입구(API·웹소켓·업로드·결제 콜백), 사람마다 따로인 데이터에 접근하는 코드
   - 볼 것: 권한 우회, 남의 데이터 접근, 인젝션·XSS·SSRF, 클라이언트 값 믿기(점수·보상·가격), 에러 처리가 없어 프로세스가 죽는 곳(예: 웹소켓 `error` 리스너 없음), 크기·개수·속도 상한 없음
   - 돌려받을 것: 심각도, `파일:줄`, 구체 공격 시나리오(입력 → 결과), 짧은 근거, 안전하다고 확인한 것 목록
   - 받은 결과 중 🔴·🟡는 해당 `파일:줄`을 직접 열어 확인한 뒤에만 "확인됨"으로 적는다.
2. **Semgrep** (설치돼 있으면): `semgrep scan --metrics=off --config p/owasp-top-ten --config p/secrets --config p/trailofbits --config p/typescript --exclude node_modules --exclude .next --exclude dist -q --json -o <임시 폴더>/semgrep.json .`
   결과 수와 함께 **에러(읽지 못한 파일) 수**를 적는다. 에러가 많으면 "앱 코드 0건"을 통과로 보지 않는다. 규칙을 못 받아 오면(네트워크) 건너뜀.
3. **의존성 점검**: lock 파일에 맞춰 `npm audit --omit=dev` / `pnpm audit --prod` / `yarn npm audit`, Python은 `pip-audit -r requirements.txt`(있으면). high 이상만 문제로 센다.

같은 문제가 여러 도구에 걸리면 하나로 합친다.

통과 기준: 🔴·🟡가 0건이고 실패한 도구가 없음. 하나라도 건너뛰었으면 "통과"가 아니라 "일부만 봄".

## 3단계. 기존 E2E 테스트

1. 프로젝트에 E2E가 있으면 설정된 명령 그대로 돌린다(예: `npx playwright test --reporter=line`). 오래 걸리면 백그라운드로 돌리되, 끝날 때까지 다른 단계는 시작하지 않는다.
2. 결과는 통과·실패·**건너뜀** 수를 모두 적는다. 실패는 테스트 이름·실패한 줄·trace 경로를 적고, 0단계의 작업 중 변경 파일과 관련 있으면 "작업 중 변경 때문일 수 있음"이라고 표시한다.
3. 건너뛴 테스트가 무엇을 검사하는 테스트인지 한 줄로 적는다(그 흐름은 검사되지 않은 것이다).

통과 기준: 실패 0. 건너뜀이 있으면 "통과(n개 건너뜀)"로 적는다.

## 4단계. 화면·API 찔러 보기

1. 로컬 서버를 0단계에서 정한 **임시 데이터**로 띄운다. 사용자가 쓰기 동작을 허락하지 않았으면 2·3번(읽기·잘못된 요청)만 하고 4번은 건너뛴다.
2. 화면 주소와 입력을 `curl`로(브라우저는 직접 조작하지 않는다. 화면과 콘솔 오류는 사람이 직접 써 볼 때 본다):
   - 주요 페이지를 받아 상태 코드와 HTML을 본다
   - 입력을 받는 API에 이상한 값: 빈 값, 5000자, `'";--`, `<script>alert(1)</script>`, 이모지. 응답 HTML에 그대로 박혀 나오면 XSS 후보
   - 없는 주소(없는 id)와 로그인해야 하는 페이지를 로그인 없이 부른다
3. API를 `curl`로 직접:
   - 로그인 없이, 다른 Origin(`Origin: https://evil.example`)으로, 빈 본문·큰 본문(수 MB)으로 각각 부른다
   - 기대: 401/403/400/413. 200이 나오거나 서버가 죽으면 문제.
4. **두 계정 시나리오** (개발용 로그인처럼 계정을 쉽게 만들 수 있을 때만): 계정 A로 0단계의 "사람마다 따로인 것"을 하나 만들고, 계정 B로 그것을 보기·고치기·지우기를 시도한다. 되면 🔴.
5. **서버가 죽을 수 있다는 지적 재현**: 2단계에서 "이 입력이면 서버가 죽는다"는 🟡가 나왔으면(예: 웹소켓에 큰 프레임), 그 입력을 이 로컬 서버에 한 번 보내 실제로 죽는지 본다. 재현되면 "실행 확인", 안 되면 "코드로만 확인"으로 적는다.
6. 로그인 후 흐름을 E2E가 이미 덮고 있으면 다시 누르지 않는다. E2E에 없는 흐름만 눌러 본다.
7. 끝나면 띄운 서버를 끄고, 이번에 **직접 만든** 임시 폴더·DB만 지운다(이름을 확인하고). `git status`가 0단계와 다르면 바뀐 파일을 그대로 두고 사용자에게 알린다.

통과 기준: 2~4번에서 기대와 다른 응답 0, 서버가 죽지 않음(없는 주소의 404는 제외).

## 5단계. 대화로 정리 + 기록

사용자에게 대화로 알려 준다. 파일 보고서는 사용자가 원할 때만 쓴다.

1. **검사한 코드**: 커밋, 작업 중 변경 여부.
2. **단계별 결과 표**: 단계 / 통과·문제 있음·건너뜀 / 걸린 수. 통과 기준은 각 단계에 적힌 것만 쓴다.
3. **찾은 문제** (심각한 순): 심각도, 한 줄 제목, `파일:줄` 또는 주소, 어떻게 하면 생기는지, 근거, 고친 뒤 확인할 명령(해당 테스트나 curl 한 줄).
4. **못 본 범위**: 건너뛴 단계·테스트, Semgrep 에러 수, 두 계정 시나리오를 못 했으면 그 사실.
5. **지난번과 비교** (지난 기록이 있으면): 새로 생김 / 해결됨 / 그대로.
6. **테스트로 남길 후보**: 이번에 찾은 문제 중 다시 생기면 안 되는 것.

심각도: 🔴 남의 데이터를 보거나 바꿀 수 있음·키 노출·로그인 우회 / 🟡 기능이 깨짐·서버가 죽음·값싼 서비스 거부 / 🟢 경고·화면 어긋남.

마지막으로 `docs/verify/site-check.md`를 덮어쓴다. 내용은 날짜, 커밋, 문제 목록(심각도·제목·`파일:줄`)만. 다음 실행의 비교 기준이 된다.

"에러가 0건"이라고 말하지 않는다. "돌린 검사에서 걸린 것은 n건, 못 본 범위는 …"이라고 말한다.
