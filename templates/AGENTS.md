# AGENTS.md (3시간 해커톤)

목표와 범위는 HUMAN.md와 docs/spec.md를 따른다. 둘 다 사람이 가져오거나 쓰는 문서라서 AI는 고치지 않는다. 빈칸이나 모호한 곳, 둘이 어긋나는 곳만 묻는다. 물어서 받은 답은 DECISIONS.md에 한 줄씩 적는다.

## 이 프로젝트
<!-- AI가 채움: 언어·프레임워크, 실행 명령, 테스트 명령. tools/harness.env와 같게. -->
- `tools/`는 hook이 AI의 수정을 막는다. 스택이 파이썬/FastAPI가 아니면 `tools/harness.env`(TEST_ALL, SRC_DIRS, CODE_GLOBS 등)와 `tools/run.sh`는 **AI가 바꿀 내용을 사람에게 보여 주고 사람이 직접 고친다.**
- 실행: `sh tools/run.sh` (서버는 `0.0.0.0`에 띄운다. localhost에만 띄우면 미리보기에서 안 열린다)
- Codex는 venv를 켠 셸에서 `codex --search --add-dir .git`으로 연다(`--search`가 없으면 웹 검색이 안 되고, `--add-dir .git`이 없으면 샌드박스가 커밋을 막는다). gate와 run.sh는 `.venv`가 있으면 알아서 그 python을 쓴다.
- 테스트 하나: `python3 -m pytest -q tests/<파일>`
- 마칠 때 검사: `sh tools/gate.sh`

## 일하는 원칙
- 모르는 건 짐작하지 말고 가정을 밝히거나 묻는다. 해석이 둘이면 둘 다 보여 준다.
- 요청받은 것만 만든다. 나중을 위한 설정, 추상화, 기능은 넣지 않는다.
- 고칠 곳만 고친다. 옆 코드를 정리하거나 서식을 바꾸지 않는다.
- 참·거짓을 가르는 일과 계산은 고정된 코드로 한다. 언어 모델은 문장을 다듬는 데만 쓴다.
- 토큰을 아낀다. 필요한 파일만 읽고, 긴 출력은 끝부분만 본다. 같은 요청을 되풀이하지 않는다.
- 목표는 3시간 안에 완성이다. 작업마다 시간 상한을 두지 않는다. 품질을 깎아서 시간을 맞추지 않고, 모자라면 시연에 안 보이는 기능부터 뺀다.

## 모델
- spec 작성 세션(사람이 따로 연다): Terra(대회 안내 기준 5.6). `/model`에서 고른다.
- 구현과 이 세션: Sol(대회 안내 기준 6.1). Astra는 대회에서 쓰지 않는다.
- 그날 `/model` 목록이 안내와 다르면 사람에게 묻는다. 외부 AI(ChatGPT·Gemini·Claude)는 쓰지 않는다.

## 흐름
1. **spec 수신**: 사람이 다른 세션에서 만든 `docs/spec.md`를 가져온다. 만드는 법은 `docs/spec-prompt.md`. spec이 없으면 구현을 시작하지 않는다.
2. **레퍼런스 조사**: 큰 작업으로 나누기 전에, spec의 MVP 기능마다 가져다 쓸 만한 공개 코드, 라이브러리, 예제가 있는지 찾고 `docs/refs.md`에 적는다. 라이브러리와 작은 코드 조각만 대상으로 한다. MVP를 이미 다 하는 완성된 앱이나 템플릿을 통째로 가져오지 않는다(대회 규칙: 외부 코드로 결과물 전체를 대체하면 안 된다). 50줄이 넘는 코드를 가져올 때는 사람에게 먼저 묻는다. 조사 결과가 작업의 크기와 개수를 바꾸기 때문에 나누기보다 먼저 한다. 10분 안팎을 권한다(코드로 막지 않는다). 쓸 만한 게 없으면 "없음"이라고 쓰고 넘어간다. 라이선스를 확인하고, 대회 규칙이 외부 코드를 막는지 의심되면 사람에게 묻는다.
3. **큰 작업으로 나누기**: 조사 결과를 반영해 TASKS.md에 적는다. 가져다 쓸 게 있는 기능은 그만큼 작게 잡는다. 개수는 정하지 않고 spec을 보고 판단한다. 기준은 셋이다.
   - 하나가 시연에서 눈에 보이는 단위일 것. 커밋 하나로 끝나는 크기.
   - 하나에 30~45분 안팎이 되게 잡는다(어림값이지 상한이 아니다). 더 잘게 쪼개지 않는다. 잘게 쪼개면 작업표를 관리하는 데 시간을 쓴다.
   - 전체 합이 남은 시간의 약 70%를 넘지 않게 한다. 나머지는 검증, 퀴즈, 마감 정리용이다.
   작업마다 `파일`(건드릴 곳), `사람 확인`(AI가 확인할 수 없는 것), `의존`(먼저 끝나야 할 작업)도 채운다. 공통 기반(데이터 모델, 레이아웃)처럼 선행 관계가 있으면 의존에 쓴다.
   나눈 뒤 사람에게 보여 주고 확인받는다. 작업 중 막히면 그 부분만 추가로 찾아 refs.md에 이어 적는다.
4. **큰 작업 반복**: 아래 "큰 작업 하나 돌리기".
5. **마감 정리**: 남은 시간이 `STOP_NEW_MIN` 아래가 되면 새 큰 작업을 시작하지 않는다. 고치기, README, 시연 순서, 마지막 커밋만 한다.

## 큰 작업 하나 돌리기
1. TASKS.md에서 다음 작업의 상태를 `진행`으로 바꾸고 시작 시각(HH:MM)을 적는다. 구현은 한 번에 하나만 돌린다.
2. **테스트 먼저**: 구현을 맡은 쪽이 완료 기준을 확인하는 테스트를 먼저 쓰고 실패하는지 본다. `implementer`에게 맡기면 테스트도 implementer가 쓰고, 메인 세션은 따로 쓰지 않는다.
3. **구현**: `implementer` 에이전트에게 맡기거나 직접 한다. 큰 작업 안에서 하위 작업을 서브에이전트로 나누는 것은 자유다. 하위 작업은 TASKS.md에 올리지 않는다. 하위 작업을 병렬로 돌릴 때는 `파일`이 겹치지 않을 때만 한다. 겹치면 순서대로 돌린다.
4. `sh tools/gate.sh`를 돌린다. FAIL이면 고친다. WARN(기존 테스트가 느슨해짐)이면 커밋하지 말고 사람에게 묻는다.
5. **검증**: `verifier` 에이전트를 새 맥락으로 부른다. 부를 때 구현 과정이나 결론을 알려 주지 않고 TASKS.md의 완료 기준과 `docs/verify.md`만 준다. 결과는 `docs/verify/<작업번호>.md`에 남는다. 지적이 있으면 구현에서 고치고 4번부터 다시 한다. 검증 에이전트는 코드를 고치지 않는다.
6. 커밋한다. 메시지에 무엇을, 왜 했는지 쓴다. 채점하는 AI가 git log를 읽는다.
7. TASKS.md 상태를 `끝`으로 바꾸고, HANDOFF.md를 덮어써서 커밋한다. 잊으면 Stop hook이 멈추지 못하게 하고 다시 시킨다.
8. **사람에게 넘기기, 다음 구현은 같이 시작**: 대기 작업이 있고 STOP_NEW_MIN 전이면 다음 작업을 `진행`으로 바꾸고 `implementer`를 백그라운드로 띄운다. 그동안 메인 세션은 사람과 아래 "사람이 할 일"을 한다: 직접 써 보기 → 바뀐 코드 읽기 → 퀴즈 5문항 → NOTES.md 메모. 사람이 방향을 바꿔야 한다고 할 만한 작업(다음 작업이 지금 결과에 달린 경우)은 띄우지 않고 기다린다.
   - 사람이 찾은 문제는 NOTES.md에 적고, 다음 구현이 끝난 뒤 고친다. 급하고 다음 구현과 `파일`이 안 겹치는 것만 바로 고친다.
   - 사람 일이 끝나면 `git add NOTES.md QUIZ.md DECISIONS.md`처럼 파일을 지정해 `docs: <번호>번 메모·퀴즈`로 커밋한다. `git add -A`를 쓰면 구현 중인 코드가 섞인다.
9. 세션을 바꿀지 판단해 권한다. 큰 작업 경계가 가장 안전하다(커밋, HANDOFF, 퀴즈가 끝난 뒤라 맥락 손실이 적다). 백그라운드 구현이 도는 동안에는 바꾸지 않는다. 토큰이 많이 쌓였으면 중간에도 권한다. 새 세션은 hook이 HANDOFF.md를 읽혀 준다.
- 사람 결정이 필요하면 바로 묻는다. 급하지 않은 것은 모아서 묻는다. 묻기 전에 보기 2~3개와 추천을 붙인다.
- 시간이 모자랄 것 같으면 범위를 줄일지 사람에게 묻는다. 뺄 기능은 시연에 안 보이는 것부터 제안한다.
- 결정할 게 없는 작은 수정은 바로 고치고 관련 테스트만 돌려 커밋한다.

## 에이전트
`.codex/agents/`에 둘이 있다. 큰 작업 안에서 필요하면 다른 서브에이전트를 더 불러도 된다.
- `implementer`: 코드를 짠다. 테스트를 먼저 쓰고, 끝나면 gate를 돌린다.
- `verifier`: 구현을 모르는 새 맥락에서 gate, e2e, 다크 패턴을 확인하고 `docs/verify/`에 보고만 쓴다. 코드를 고치지 않는다.
- 메인 세션은 사람과 대화하고 레퍼런스 조사, HANDOFF, 퀴즈를 맡는다.

## 스킬
- `.agents/skills/`는 Codex가 자동으로 읽는 기본 스킬이다. 퀴즈는 `quiz`, e2e 테스트 코드는 `webapp-testing`(단언하는 테스트 코드로만 쓰고 AI가 스크린샷을 보고 판단하지 않는다. Playwright가 없으면 TestClient 테스트로 대신한다), 버그는 `systematic-debugging`, `끝`으로 바꾸기 전엔 `verification-before-completion`을 따른다.
- 과제에 맞는 스킬이 기본에 없으면 키트를 clone한 폴더의 `library/`(보통 `~/kit/library`)에서 `library/INDEX.md`를 보고 골라 `cp -r ~/kit/library/<분야>/<스킬> .agents/skills/`로 꺼낸다. 꺼냈으면 DECISIONS.md에 한 줄 적는다. 한꺼번에 많이 꺼내지 않는다(세션마다 설명이 맥락에 들어간다).
- 스킬 지침이 이 문서와 부딪히면 이 문서를 따른다. 특히 테스트 개수와 순서, 답의 길이, 코드 지우기, 파일을 어디에 쓸지, 커밋·브랜치, 사람에게 묻는 방식, 다른 스킬을 꼭 부르라는 지시가 그렇다. 스킬이 계획서·명세서를 따로 쓰라고 해도 쓰지 않는다(TASKS.md, DECISIONS.md, docs/refs.md에 적는다). 스킬이 부르라는 다른 스킬이 없으면 건너뛴다.
- 브라우저를 직접 조작하거나 화면 캡처를 보고 판단하라는 스킬 지시는 따르지 않는다(대회의 Computer Use 금지).

## 사람이 할 일
사람이 승인만 하는 3시간이 되지 않게, 큰 작업이 끝날 때마다 아래를 사람에게 요청한다.
1. **직접 써 보기(5~10분)**: TASKS.md의 `사람 확인` 칸을 목록으로 안내하고, 사람이 화면에서 직접 눌러 본다. 불편한 점은 사람이 NOTES.md에 한 줄씩 적는다. AI는 그중 고칠 것을 다음 작업이나 DECISIONS.md에 반영한다.
2. **바뀐 코드 읽기**: 바뀐 파일과 핵심 위치를 안내한다. 퀴즈는 읽은 내용으로 낸다.
3. **퀴즈**: 객관식 5문항을 낸다(아래).
4. **NOTES.md**: 사람이 "왜 이렇게 만들었나"를 두세 줄로 직접 적는다. AI가 대신 쓰지 않는다. 서술형 때 그대로 꺼내 쓰는 용도다.
- AI가 도는 동안 사람은 시연 순서, README 문구를 미리 쓴다.

## 퀴즈
큰 작업이 끝나면 객관식 5문항을 낸다. 목적은 사람이 AI가 만든 것을 이해하고 있는지 확인하는 것이다.
- 보기는 4개, 정답은 하나. 5문항을 메시지 하나로 한 번에 내고 답도 한 번에 받는다(예: `1A 2C 3B 4D 5A`).
- 문제는 이번 큰 작업에서 실제로 바뀐 코드와 결정에서 낸다. 일반 상식 문제는 내지 않는다.
- 5문항 중 최소 2개는 이해 문항이다: "왜 이 방식으로 짰나", "이 코드가 깨지면 어디서 보이나", "이 값을 바꾸면 무엇이 달라지나".
- 정답은 사람이 답한 뒤에 한꺼번에 알려 준다. 맞아도 한 줄 해설을 붙인다.
- 틀린 문제는 `QUIZ.md`에 문제, 사람의 답, 정답, 해설을 남긴다. 틀린 개념은 다음 작업에서 한 번 더 물을 수 있다.
- 정답이 모호하거나 코드에서 확인되지 않는 문제는 내지 않는다.

## 문서
- **docs/spec.md**: 외부 세션에서 가져온 명세서. AI는 고치지 않는다. 바꿀 점은 제안만 하고 사람이 고친다.
- **docs/refs.md**: 레퍼런스. 링크, 가져올 부분, 라이선스.
- **docs/verify.md**: 검증 체크리스트. 결과는 `docs/verify/<번호>.md`.
- **NOTES.md**: 사람이 직접 쓰는 메모. AI는 고치지 않는다.
- **DECISIONS.md**: 선택할 일이 있을 때마다 한 줄. 무엇을 골랐나, 왜, 다른 선택지는 뭐였나.
- **HANDOFF.md**: 큰 작업이 끝날 때마다 틀의 칸을 모두 채워 덮어쓴다. 커밋·작업 상태·안 올린 변경 같은 사실은 Stop hook이 턴마다 `.codex/handoff-auto.md`에 자동으로 남긴다. 새 세션이 열리면 hook이 두 파일을 함께 읽혀 주니 따로 찾아 읽지 않는다. 쓰는 규칙:
  - 이 대화를 모르는 새 세션에게 쓴다. 사람용 요약이 아니다.
  - 해 봤는데 안 된 것과 그 이유를 꼭 쓴다. 안 쓰면 새 세션이 같은 실수를 되풀이한다.
  - 실행해서 확인하지 않은 것은 "확인 안 한 것" 칸에 둔다. 추측이 사실처럼 적히면 새 세션은 다시 확인하지 않고 믿는다.
  - 커밋, diff, DECISIONS.md에 이미 있는 내용은 복사하지 않고 위치만 적는다.
  - 다음 한 걸음은 파일·함수·명령까지 적는다. "날짜 처리 고치기"가 아니라 "`app/parse.py`의 `parse_time()`이 `2026/10/21` 형식을 못 읽음 → 형식 추가 후 `pytest tests/test_parse.py`".
  - 키, 토큰, 개인 정보는 쓰지 않는다.
- 대화가 자동 요약(compact)됐으면 이어 가지 말고 HANDOFF.md를 쓴 뒤 새 세션을 권한다. 요약되면 앞서 정한 것이 흐려진다.
- **README.md**: 제출용. 실행 방법, 확인한 것(테스트·화면), 남은 한계를 채운다. 과제가 요구하는 파일 이름과 형식이 따로 있으면 그걸 따른다.

## 하지 않는 것
- HUMAN.md, docs/spec.md, NOTES.md, `tools/`, `.codex/` 수정 (hook이 막는다)
- 기존 테스트를 지우거나 skip 붙이기
- 300줄 넘는 코드 파일 (gate가 잡는다)
- 키·토큰을 코드나 문서에 쓰기, 작업물을 밖으로 보내기, git push
