# 검증 체크리스트

큰 작업이 끝날 때 `verifier`가 위에서부터 본다. 해당 없는 항목은 `해당 없음`과 이유를 한 줄 쓴다. 모든 항목은 명령을 실행하거나 HTML·코드를 읽어서 확인한다. 브라우저를 직접 조작하거나 스크린샷으로 판단하지 않는다(대회의 Computer Use 금지). 눈으로 보는 확인은 사람이 직접 써 보기에서 한다.

## 1. 기본
- [ ] `sh tools/gate.sh` 통과
- [ ] TASKS.md의 완료 기준을 하나씩 실제로 실행해 확인
- [ ] spec.md의 해당 기능이 응답·HTML에 spec대로 들어 있다

## 2. e2e
- [ ] `tests/e2e/`가 있으면 돌린다(Playwright가 깔려 있을 때만. 없으면 "확인 불가: Playwright 없음")
- [ ] 앱을 새로 띄워서 시작한다(캐시된 상태에 의존하지 않는다)
- [ ] spec의 "사용 순서"를 처음부터 끝까지 HTTP 요청(curl, TestClient)으로 따라 간다
- [ ] 빈 입력, 너무 긴 입력, 중복 제출을 한 번씩 넣어 본다
- [ ] 새로고침 후에도 상태가 맞다(저장이 있는 경우)
- [ ] 서버 로그에 에러가 없다(브라우저 콘솔은 사람이 써 볼 때 본다)

## 3. 다크 패턴 (사용자를 속이거나 몰아가는 화면)
- [ ] 거절·취소·닫기 버튼이 승인 버튼보다 작거나 흐리거나 숨어 있지 않다
- [ ] 동의·구독·수집 체크박스가 기본으로 켜져 있지 않다
- [ ] 거절 문구가 죄책감을 주지 않는다("싫어요, 손해 볼래요" 같은 식)
- [ ] 가짜 긴급성·희소성이 없다("마감 임박", 근거 없는 남은 수량, 가짜 타이머)
- [ ] 마지막 단계에서 처음 안 보이던 비용·조건이 나타나지 않는다
- [ ] 가입보다 해지·삭제가 어렵지 않다
- [ ] 같은 확인을 반복해서 요구하지 않는다
- [ ] 알림·결과·점수가 실제 데이터와 다르게 부풀려 보이지 않는다(AI 응답의 단정 포함)

## 4. 보고
`docs/verify/<작업번호>.md`에 결과, 지적, 확인 불가, 확인한 것을 쓴다.
